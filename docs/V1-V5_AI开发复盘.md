# 从一条时间轴到中国航天数字博物馆

## V1 → V5：一次 Human × ChatGPT × Codex 协作开发实验

这篇文章不是把 CHANGELOG 重新排版，也不是为一个已经完成的网页补写漂亮的宣传词。它试图回答一个更实际的问题：一个最初只想“把中国航天史做成更直观的网页”的项目，为什么会逐步长成包含五大发展主线、五座主题展厅、来源登记、自动截图、浏览器 QA、本地启动器和 GitHub Pages 的数字博物馆；在这个过程中，人、ChatGPT 和 Codex 分别承担了什么；又有哪些看起来合理的 AI 结果，必须被人工否定、缩小或重做。

项目最终的正式版本是 V5.0。它首先是一个 PC 桌面端数字展馆，主要验收视口为 1600×900；移动端和平板端没有在 V5.0 中正式收口。这一限制不是遗漏，而是一次有意识的范围控制。

还必须先说明历史边界：**V1～V4.2 为 Git 正式管理前的项目历史回顾，根据现有项目文件和开发记录整理，不代表这些阶段当时存在对应的 Git 提交或 Tag。** V4.2 之后才可以依据真实 Git 提交、Tag、迭代文档和开发日志书写版本历史。下面不会为 Git 之前的阶段伪造 commit、分支或发布记录。

## 01 项目为什么开始

中国航天史适合被理解，却不适合只被压缩成一篇长文章。1956 年的体系建立、1970 年的东方红一号、载人航天、北斗、探月、火星探测和空间站，并不是一串互不相关的年份。它们之间有时间关系，也有任务关系、技术继承和能力扩展关系。

普通文章能够解释一个事件，普通时间线能够回答“什么时候发生了什么”，但很难同时让读者看见：为什么火箭能力会连接到卫星、载人和深空任务；为什么探月要经历“绕、落、回”；为什么火星任务的难点不只是距离远，而是发射窗口、转移轨道、通信时延和自主运行共同改变了工程条件。

项目的起点因此很朴素：做一个网页，让中国航天发展史可以被看见、点击和比较。最初并没有“数字博物馆”这么完整的目标，先有的是一条时间轴，以及把历史从文字中搬到空间界面的愿望。

## 02 整体演化图

| 阶段 | 主要形态 | 解决的问题 |
| --- | --- | --- |
| V1 | 中国航天史时间轴 | 先把历史讲出来 |
| V2 | 航天视觉交互网页 | 让历史有空间感和观看体验 |
| V3 | 数据与数字资产系统 | 从写页面转向管理内容 |
| V4 | 五大主题数字展厅 | 从专题网页变成数字博物馆 |
| V5 | 策展、来源、自动 QA、产品化与正式发布 | 从能看变成可维护、可验证、可发布的数字产品 |

也可以把它写成一条更短的流程：

```text
资料展示
  ↓
视觉网页
  ↓
内容工程
  ↓
数字博物馆
  ↓
可维护、可验证、可发布的正式展馆
```

这条变化并不是一次架构设计会直接得到的结果。每个阶段都暴露出上一阶段没有解决的问题：视觉会掩盖内容，内容会挤压阅读，素材会带来来源和许可问题，五个页面会逐渐趋同，AI 生成速度会让仓库快速膨胀。版本迭代的价值，正在于把这些问题显性化。

## 03 V1：基础时间轴

V1 的核心工作是建立时间结构。对于刚开始的项目，时间轴是一个合理的第一步：它有明确的输入和输出，能够把零散的航天事件放在同一条可读的时间线上，也能帮助开发者发现年份、事件名称和叙述之间的缺口。

时间轴首先解决了“什么时候发生什么”。它把中国航天事业起步、东方红一号、载人航天、探月和行星探测放在一个共同坐标系里，让读者不必在多篇资料之间来回跳转。这个阶段的重要性不在于页面复杂，而在于先建立一份可以持续修正的历史骨架。

但一条时间线很快显示出自己的边界。它擅长线性顺序，不擅长表达并行发展；擅长显示节点，不擅长解释能力传承；可以把嫦娥一号和天问一号标在不同年份，却不能仅靠位置说明它们为什么共享运载、测控和深空导航等基础能力。V1 留下的第一个问题就是：航天史不是只有一条线。

## 04 V2：星空与航天视觉

V2 开始加入星空、航天器、轨道和初步交互。历史事件不再只是文本列表，而是被放进一个更有空间感的界面。Three.js 等技术让网页可以表现星体、轨迹和深色背景，访问者获得了“进入航天场景”的感觉。

这种变化很有吸引力，因为航天主题天然容易和黑色、深蓝、发光轨道联系起来。但它也带来一个后来反复出现的陷阱：科技感很容易变成 AI 网页感。全黑背景、霓虹蓝、发光边框、玻璃卡片、渐变和装饰轨道，能够迅速制造“未来”印象，却不一定帮助读者理解历史。

当每一个模块都在发光，每一条线都像要传输数据，每张卡片都用同样的深色样式，页面看起来可能更像产品 Landing Page 或 SaaS Dashboard，而不是一个需要阅读、比较和停留的博物馆。V2 的价值并不是证明这种视觉永远正确，而是让项目亲自经历了“好看”和“好展览”之间的差别。V5 后来重新采用深色 Hero 加浅色纸张式正文，正是对这个阶段经验的回应。

## 05 V3.1：结构化数据

随着事件、任务、火箭和展厅内容增加，把文字继续直接写在 JSX 里会变得越来越难维护。一个标题的修改可能需要在多个组件里查找；同一事件在首页、时间线和展厅中出现时，容易出现年份不一致；不同页面各自保存一份任务信息，也会使事实核验变得困难。

V3.1 开始把内容从页面结构中抽离出来，形成“数据 → 组件 → 展示”的关系。航天事件、任务、火箭、展厅、时间线和任务过程逐步拥有独立的数据结构，React 组件负责解释这些数据，页面负责安排观看顺序。

这不是单纯的工程整理。内容结构化之后，才有可能对数据做检查，才有可能让同一个任务同时出现在首页时间线、主题主线、展厅节点和任务详情中，也才有可能在事实不确定时删除一个字段，而不是在十几个页面里寻找同一句话。对于一个历史主题项目，数据模型本身就是策展工具的一部分。

## 06 V3.2：数字资产管理

图片的加入让项目更接近展览，也让问题变得更复杂。最初的思路很容易是“找一张好看的图片”，但图片在博物馆里不是纯装饰。它可能是任务现场影像、模型、复制品、结构示意、历史档案、新闻图片或技术资料；不同身份会影响标题、说明、来源、许可和它在页面中的位置。

因此 V3.2 开始让图片拥有更多上下文：任务对应关系、来源、媒体类型、主视觉或辅助角色、质量、真实影像/模型标识和使用状态。图片登记和来源数据逐步形成独立系统。

这一变化把“图片资源”转成了“数字展品”。同一张神舟五号模型图不能被误写成真实任务现场；一张官方网页图片如果许可不明确，就不应因为视觉效果好而被随意下载；一张开放许可图片可以本地使用，但仍需要保留作者、原始标题和许可信息。展览质量的一部分，来自展品身份是否诚实。

## 07 V3.3：图片自动采集和质量评分

当素材数量增加，手工逐张搜索会变慢，于是项目加入了自动搜索、尺寸判断、质量排序和候选管理工具。程序可以帮助扩大候选集，快速过滤过小、比例不合适或明显不适合展示的图片，也能减少重复的机械劳动。

但自动化没有替代策展判断。程序可以判断像素尺寸，却不能可靠判断一张图是否真正解释了当前章节；可以找到包含“火星”关键词的图片，却不能保证它是天问一号真实任务影像；可以识别一个网页上的许可证文本，却不能自动消除来源链条中的歧义。

这个阶段形成了一个重要原则：**自动工具负责扩大候选集和提供证据，人负责决定哪些内容进入展览。** 如果把排序结果直接当成最终答案，项目就会从“资料管理”退回“相关图片堆积”。

## 08 V3.4：重点航天素材

东方红一号、长征、神舟、嫦娥、天宫和天问逐渐成为真实展项。项目开始使用历史报道、任务影像、结构图、模型和空间场景来承载内容。页面比纯文字更有记忆点，访问者也可以通过展品进入具体任务。

然而“有展品”不等于“有展览”。一张漂亮的火箭照片不能自动解释运力意味着什么，一张火星影像不能自动解释行星际通信为什么困难，一张航天员照片也不能自动讲清楚从无人验证到长期驻留的能力链。V3.4 让素材更丰富，也让“图片与叙事的关系”成为下一阶段必须解决的问题。

## 09 V4：数字博物馆诞生

V4 没有继续把内容简单分成“火箭、卫星、飞船、月球、火星”五个百科目录，而是开始按访客理解问题组织展厅。最终形成五大发展主线：进入太空、天基中国、人在太空、奔向月球、走向行星。

“进入太空”回答中国如何获得独立进入轨道、把越来越大的任务送往更远地方的能力；“天基中国”回答卫星如何从单颗试验设备变成导航、气象、遥感和社会服务；“人在太空”回答如何从无人验证走向载人飞行、交会对接和长期驻留；“奔向月球”通过绕、落、回呈现能力逐级增加；“走向行星”解释距离和时间如何改变任务工程。

五条主线并不是五个孤岛。运载能力支撑卫星、载人和深空任务，测控连接不同距离的航天器，导航、材料、制造和空间科学又为多个方向提供底座。数字博物馆的核心转变，是从“展示很多东西”变成“帮助访客理解它们之间的关系”。

## 10 V4.1：中文化与图片角色

V4.1 继续处理界面中文化、字体、字号、图片标注和展品身份。中文 UI 不是把英文按钮逐个翻译完就结束，还需要考虑中文段落的行长、标题换行、信息密度和阅读节奏。

图片说明也开始区分馆藏展品、模型、真实任务影像、历史档案和暂无公开影像。一个模型可以帮助理解飞船结构，但不能冒充发射现场；一个官方链接可以作为可靠入口，但不等于项目已经获得本地复制授权；一张中文重绘 SVG 可以用于技术解读，但必须说明它是重绘而不是官方原图。

这一步让页面更加诚实，也为后来的来源与许可体系铺路。

## 11 V4.2：第一个完整数字博物馆基线

V4.2 形成了第一个相对完整的数字博物馆基线：有首页、五条主线、五座展厅、时间线、火箭谱系、三维场景、图片浏览和中文展陈。它已经不再是一个只有单页时间轴的实验，而是具备完整观看路径的网页应用。

这里必须再次强调，V4.2 及以前属于 Git 正式管理前的历史回顾。后续文档可以根据现有文件、图片、数据、AI 开发记录和迭代材料整理这一时期，但不能把整理出的阶段写成当时已经存在的真实提交或 Tag。

## 12 为什么 V4 已经能看，却还需要 V5

V4 的问题不是“功能不够多”，而是功能和内容之间的关系还不够成熟。

第一，五厅在结构上逐渐变得相似。只更换颜色、标题和图片，仍然会让访客感到五个页面是同一个模板的不同副本。第二，AI 科技风过重，深蓝、发光和卡片会把历史资料包装成产品功能。第三，图片虽然相关，却不一定承担叙事；展品在页面中出现了，但它为什么重要、处于哪一段能力链，仍然不够清楚。第四，来源信息过于技术化，作者、URL、许可和授权说明如果全部直接铺开，会抢走普通阅读层的注意力。第五，字体和布局反复调整，说明页面缺少稳定的层级 token。第六，页面缺少自动 QA，人工看过一页并不能证明五厅都没有资源错误或横向溢出。第七，内容越来越多，但主次没有同步变清楚。

所以 V5 的目标不是再增加更多东西，而是收束、分层、验证和发布。

## 13 V5-E3：重新建立视觉基底

V5-E3 把首页和五个展厅重新放回数字博物馆语境。深色用于 Hero、展厅开场和确实需要空间感的示意场景；正文转向暖纸白、冷灰白、灰紫白和沙灰等浅色展陈背景。这样的对比让深色更像展厅入口，而不是整站的默认产品皮肤。

视觉原则可以概括为：博物馆大于 AI SaaS Dashboard。页面不再用发光线条和玻璃卡片证明自己“科技”，而是让展品、历史节点、说明文字和观看关系成为主体。来源、作者和许可证详情默认折叠，普通访客先看到机构、年份和来源详情入口，需要深入核查时再展开完整登记。

E3 也建立了五大发展主线、五个 Grand Hall、路由和五种差异化任务过程的基础。它没有消除所有问题，却把问题放到了正确的结构里。

## 14 V5-E4：第二层重点展项

E4 解决“展厅有正文但缺少重点展品”的问题。每个展厅增加数字博物馆的第二层：进入太空突出长征五号等大推力能力，天基中国突出卫星应用，人在太空组织载人章节，奔向月球组织探月能力，走向行星组织深空距离与任务工程。

Deep Dive 的意义不是把页面变得更长，而是为访客提供停留点。一个重点展项需要有清楚的身份、解释和来源，它应该把前面的主线变成可以观察的证据，而不是再生成一排同样大小的营销卡片。E4 也因此开始处理媒体布局、标题安全区、轻量导览和不同内容块之间的垂直节奏。

## 15 V5-F：五厅去模板化

F 是 V5 最重要的结构性收束之一：五厅最终不再共用统一三列卡片，而是让每个展厅拥有自己的知识结构。

进入太空采用“尺度”。六枚火箭连续排列，通过高度、近地轨道运力、轨道类型和代表任务，回答把越来越大的东西送到不同地方需要什么能力。天基中国采用“观察与应用”，以“我在哪里？天气正在发生什么？从太空能看清什么？”连接北斗、风云和高分，再把卫星连接到数据、服务和社会生活。人在太空采用“章节”，沿无人验证、首次载人、出舱、交会对接、空间站和长期驻留推进。

奔向月球采用“路线”，把嫦娥一号、三号、五号放入绕、落、回的动作链，同时把月背通信、软着陆和采样返回作为工程支路，而不是附加装饰。走向行星采用“距离与工程约束”，把发射窗口、转移轨道、飞行时间、通信时延、自主运行和深空测控放回任务链，天问一号以绕、落、巡形成闭环。

去模板化不意味着每个页面都要完全不同，而是每个页面的布局都服务于自己的问题。结构差异来自知识差异，而不是来自换色。

## 16 RC1：PC 深度终审

进入 RC1 后，项目范围被明确冻结为 PC 桌面端，主要验收视口是 1600×900。这个决定让团队可以集中检查实际展示效果，而不是同时追逐多个尚未稳定的断点。

RC1 关注性能、lazy loading、Three.js chunk、字体、展陈、路由和图片。首页和展厅页面通过路由懒加载拆分，入口 JS 降到约 218 KB，SpaceScene 独立 chunk 仍约 817 KB。后者有构建警告，但它已经被拆分并延迟加载，因此没有为了消灭一个警告而重新设计三维架构。

这也是字体和页面密度反复被看到的阶段。屏幕上“能放下”不代表“读起来舒服”；一个段落如果只有 13 或 14px，即使没有技术溢出，也可能在真实显示器上失去展览阅读感。

## 17 自动截图体系

项目后来固定生成六张 PC fullPage 截图：`01-home`、`02-launch`、`03-satellite`、`04-human`、`05-lunar`、`06-planetary`。每张截图使用 1600×900 浏览器视口，保存的是完整长页面。

截图不是装饰性的交付物，而是 AI 执行与人工视觉验收之间的接口。代码层面可以报告构建成功，浏览器层面可以报告页面没有异常，但只有截图能让人快速观察：标题是否抢占半屏，正文是否太小，来源卡是否穿插主线，图片是否破坏连续比较，五厅是否真的不再同构。

截图脚本还自动检查同源 404、page error、console error、broken image、缺失 alt、空链接名称和 1600px 横向溢出。自动检查不能替代审美，但能把明显的工程问题挡在人工验收之前。

## 18 为什么冻结 Mobile

在同一轮同时维护 PC 和 mobile，会让每次字号、间距和卡片调整都产生多套连锁影响。页面长、内容多、展厅结构又各不相同，移动端很快会把“收口”重新变成一轮全面重构。

因此 V5.0 先只收口 PC。这个决定并不是认为移动端不重要，而是承认项目一次只能稳定完成有限范围。范围冻结让正式版有明确的验收边界，也避免为了展示“兼容更多设备”而牺牲 PC 展陈质量。

## 19 RC2：产品化

RC2 把项目从本地开发页面推进到普通用户可以访问的产品：加入 GitHub Pages、在线展馆、本地一键启动和 Microsoft Edge 入口。Vite 的 `base` 设置确保仓库子路径 `/China-Space-Museum/` 下的资源可以正确加载。

本地启动器保持纯 CMD：检查依赖，调用 `npm.cmd run dev`，打开 Edge，不安装依赖、不下载文件、不执行远程脚本。它的意义不在于功能复杂，而在于让没有开发背景的人也有明确入口。

## 20 PowerShell 杀毒软件误报事件

项目曾创建过 `scripts/start-museum.ps1`。在用户环境中，安全软件启发式报告了 `HEUR:TrojanDownloader/PS.NetLoader`。后续通过日志检查，没有发现明确的恶意下载行为证据，但这并不意味着应该让用户关闭杀毒软件、建立白名单或忽略告警继续使用。

最终的处理是彻底废弃 `.ps1` 方案，改成纯 `中国航天博物馆启动器.cmd`。正式启动器不下载远程文件、不执行远程脚本、不使用 Base64、不提权、不修改注册表、代理、VPN、防火墙或安全软件设置。

这件事留下的经验很重要：**AI 写出的技术上可用方案，不一定是用户环境中最合适的方案。** 可靠性不仅是程序能否启动，也包括用户是否能理解它、系统安全软件是否会将其视为高风险、失败时是否会留下可解释的状态。

## 21 RC3：内容、事实、来源终审

RC3 开始把内容事实核验、来源层级和规划状态放到正式验收中。历史节点不能只因为“看起来合理”就写入；火箭参数不能把不同构型、不同轨道指标混在一起；规划中的长征十号和后续行星任务不能写成已经完成。

这一阶段优先使用国家航天局、中国载人航天工程官网、北斗官网、中国气象局、中国科学院等权威来源，必要时使用新华社、人民日报等可靠历史资料辅助。无法稳定核验的数字宁可删除，改成定性描述。V5.0 最终删除了长征十号原有的具体高度和地月转移运力数字，保留“面向载人月球探测的地月转移能力（规划）”。

来源界面也开始分层：普通阅读层只显示机构、年份、必要的许可简写和来源详情入口；作者、原始标题、URL、许可、授权说明和使用状态放在展开登记中。这样既不掩盖证据，也不让元数据压过展品。

## 22 RC4：最后策展去模板化

RC4 不是新架构，而是最后的策展收口。五厅必须有自己的故事，而不仅是不同颜色。最终的知识结构分别是：进入太空的运力—轨道—任务边界，天基中国的问题—数据—服务，人在太空的无人—载人—对接—空间站—长期驻留，奔向月球的绕—落—回与月背支路，走向行星的距离—时间—通信—自主—绕落巡。

首页也从“入口页面”变成序厅：Hero 负责建立主题，五条主线负责导航，入馆导言解释能力如何外扩，关键时刻承担历史展墙，技术底座说明多条主线如何共享能力。页面不再依靠巨型标题、发光线路或大量新增 Section 证明自己完成了迭代。

## 23 V5.0 正式发布

V5.0 正式发布前完成了生产构建、浏览器 QA、六张 PC fullPage 截图、启动器检查、事实审计和 Git 发布。正式 commit 是 `bff5bc9a96bff0c50c4fd13e84b77598463399f2`，annotated tag 是 `v5.0`，并且永久指向该 commit。GitHub Pages workflow 成功，线上页面通过首页、五厅和旧任务页检查。

正式发布的价值不只是“代码在 main 分支”。它还包括：截图目录只保留正式六张图，源码与素材没有因为迭代被随意删除，构建警告被记录而不是被掩盖，历史文档可以追溯，来源规则被写下来，启动方式对用户可解释。

## 24 V5.0 首页现在在讲什么

首页不是 SaaS Landing Page，也不是把所有展厅卡片堆在一起的目录。它是数字博物馆的序厅。

第一层是主题：深色 Hero 用“中国航天发展史”建立进入展馆的感觉。第二层是五条主线：它们不是五个孤立按钮，而是把航天史的不同能力方向放到同一个历史坐标中。第三层是入馆导言：建立体系、进入轨道、把人送入太空、长期在轨、探月、月背和行星际，能力边界逐步外扩。第四层是关键时刻：以历史展墙方式提供约六个具有代表性的节点。第五层是共同技术底座：运载、测控、导航、材料与制造、空间科学如何支撑前面多条主线。

## 25 五个展厅现在分别讲什么

进入太空的核心问题是“能把多大的东西送到哪里”。火箭谱系的连续比较是主体，长征五号和长征二号 F 的媒体是辅助证据。

天基中国的核心问题是“卫星为什么和普通人的生活有关”。东方红一号是历史起点，北斗、风云和高分分别回答位置、天气和地表观测问题。

人在太空的核心问题是“如何从一次飞行走向长期驻留”。神舟一号至四号的无人验证、神舟五号首次载人、神舟七号出舱、交会对接和空间站建造形成章节。

奔向月球的核心问题是“绕、落、回为什么代表逐级增加的能力”。嫦娥六号月背采样返回作为当前线路的重要收束，通信、中继、采样、起飞、交会和返回共同构成工程逻辑。

走向行星的核心问题是“距离为什么会让工程越来越难”。天问一号以绕、落、巡形成一次完整闭环，祝融号提供火星表面工作的实例，后续方向保持规划状态。

## 26 来源与媒体许可体系

项目采用两种主要媒体策略。第一，官方页面和官方任务影像在许可不明确时保持 link-only，用户通过来源卡进入国家航天局、中国载人航天工程官网或其他可靠机构页面。第二，明确开放许可的素材才进入本地资源，并在来源登记中保留作者、原始标题、许可和用途信息。

普通阅读层和完整来源登记层分开，是为了同时照顾可读性和可追溯性。访客首先看到“机构 · 年份 · 来源详情”，研究者展开后可以看到更完整的登记。来源不明确的素材不因为视觉效果好就进入正式展陈，视频也不下载、不嵌入未知第三方播放器。

## 27 Human / ChatGPT / Codex 分工

Human 提出目标，描述实际体验，指出哪里难读、哪里像模板、哪里不值得保留，并作最终审美和内容取舍。人工验收不是最后签字，而是持续提供方向的过程。

ChatGPT 负责分析问题、组织架构、提出策展方案、进行网络检索、编写 Codex Prompt、规划版本和审查截图。它更像一个能够把模糊感受转译成约束和验收标准的协作层。

Codex 负责读取项目、修改代码和 CSS、维护数据、运行 build、生成截图、执行浏览器 QA、处理 Git、Tag、Push 和 Pages 验证。它擅长把清晰的目标变成可执行的文件变化和检查结果。

流程可以概括为：

```text
Human
  ↓ 目标 / 体验 / 判断
ChatGPT
  ↓ 结构化方案 / Prompt / 验收条件
Codex
  ↓ 代码 / 构建 / 截图 / Git
Human + ChatGPT
  ↓ 视觉与内容验收
下一轮有限范围迭代
```

## 28 AI 做错过什么

这个项目不能只展示最终结果，因为错误正是协作经验的来源。AI 曾经把“科技感”推得过远，让页面接近深蓝 Dashboard；五厅一度不断趋同，靠颜色而不是知识结构区分；字号出现忽大忽小，正文为了容纳内容被压得太小；页面会自动扩大任务范围，把移动端、更多媒体或新的 Section 一起带进来；图片虽然相关，却不承担叙事；事实数字看似合理，却没有稳定的一手证据；来源卡一度可能抢走主内容；截图副本会让仓库膨胀；PowerShell 启动器在真实环境中触发安全误报；网络 Push 也可能失败。

这些错误有共同模式：生成系统倾向于增加，人工判断经常需要删除。AI 很容易把“还有什么可以加”当作进度，但展览设计经常要问“什么应该不出现”。

## 29 为什么人工验收不可替代

AI 很擅长生成候选页面、候选文案和候选素材，却不会自动知道什么应该删、哪个展品应成为主展品、五厅是否已经像同一个模板、正文是否需要靠近屏幕才能阅读、来源是否抢了主体，以及什么时候应该停止优化。

自动 QA 可以告诉我们一张图片自然宽度为零，不能告诉我们这张图片在叙事中是否放错位置；可以告诉我们没有横向溢出，不能告诉我们一段中文是否密得让人不愿意读；可以告诉我们构建成功，不能告诉我们首页第一眼像博物馆还是像产品官网。

人工验收因此不是与 AI 对立的“最后挑错”，而是把项目从可生成状态带到可使用状态的必要环节。

## 30 Git 为什么重要

Git 让项目拥有了可追溯时间。Commit 记录一次具体变化，Tag 标记一个稳定发布点，Prompt 保存当时如何提出目标，Iteration 记录为什么这样改，Screenshot 保存人工看到的结果，CHANGELOG 提供简短索引，AI Development Log 记录协作过程。

尤其重要的是，Git 也能防止历史被想象填补。V1～V4.2 没有真实 Git 提交，就明确写成 Git 前历史；V4.3、V4.4、V5.0-E3、V5.0-E4、V5.0-F、RC1、RC2、RC3、RC4 和 V5.0 则依据实际提交与 Tag 书写。正式版不只是某个文件夹里的一组代码，而是一个可以被别人检查的时间点。

## 31 Prompt 的变化

最初的请求可能只是“帮我做得漂亮一点”。随着项目变复杂，Prompt 逐渐包含目标、禁止事项、验收标准、范围边界、Git 行为、来源规则和安全约束。

高质量 Prompt 不等于越长越好。它的进步在于把“漂亮”变成可观察的原则：正文要可读，五厅不能只换颜色，来源不应抢主内容，规划不能写成已完成，截图固定 1600×900，移动端冻结，Git 不得 force push，启动器不能下载远程脚本。约束越清楚，AI 越不容易用额外工作掩盖真正的问题。

## 32 V1 → V5 真正发生的变化

界面从时间轴变成航天视觉网页，再变成数据和数字资产系统，随后变成五大主题数字展厅，最终成为经过策展去模板化、来源与事实核验、自动截图/QA、Git/Tag/Pages 发布的正式产品。

开发方法也发生变化：人工描述 → AI 生成 → 版本迭代 → Git 追踪 → 自动截图 → 来源核验 → 自动 QA → 正式 Release。技术栈并不是最深的变化，真正变化的是项目开始把内容、视觉、证据、范围和发布都当作同一件工程来管理。

## 33 V5.0 当前已经具备什么

内容上，它具备首页、五大发展主线、五座主题展厅、历史时间线、火箭谱系、任务过程和任务详情；展陈上，五厅拥有不同的知识结构；媒体上，它区分开放许可本地素材和官方 link-only 入口；技术上，它使用 React、Vite、Three.js、React Three Fiber 和路由懒加载；本地使用上，有纯 CMD 启动器；在线使用上，有 GitHub Pages；质量上，有 build、截图和浏览器 QA；项目管理上，有真实 commit、Tag、Prompt、Iteration、CHANGELOG 和开发日志。

这并不代表它已经没有限制。V5.0 只正式支持 PC，Three.js 仍保留较大的独立 chunk，部分历史素材的授权维护仍需要长期更新。正式版的成熟，不是消灭所有未来工作，而是明确知道哪些工作不属于当前版本。

## 34 最重要的经验

1. 不要一开始就要求 AI 做完整网站。先解决一个清楚的问题，再让结构在真实使用中暴露问题。
2. 截图比“已修改完成”更重要。代码变化必须回到页面和真实视口中检查。
3. Prompt 应表达设计原则，而不只是 CSS 数值。知道为什么调整，比知道调整多少更重要。
4. 不要害怕推翻 AI 结果。生成得快，不等于结果就该保留。
5. Git 越早引入越好。没有可追溯历史，后续复盘很容易变成猜测。
6. 内容越多不代表展览越好。主次、关系和停留点比数量重要。
7. 范围冻结很重要。一次只收口一个设备范围，才能真正完成验收。
8. AI 实现速度快，但不会自动替代判断。
9. 来源与许可必须从后期补救变成前期规则。
10. 到一定阶段必须停止继续优化。V5.0 首先要成为一个稳定的版本，而不是永远处于下一轮修改中。

## 35 为什么保留失败记录

这个仓库不仅展示最终网页，也希望展示它为什么最终变成这样。失败记录能解释为什么页面从发光卡片转向纸张式正文，为什么五厅必须去模板化，为什么一个看似合理的具体数字最终被删掉，为什么启动器放弃 PowerShell，为什么移动端被冻结，为什么截图目录需要清理。

对 AI 协作而言，失败不是丢脸的附录。它们说明哪些判断不能交给自动生成，哪些约束应该更早写进 Prompt，哪些外部环境问题不能靠技术炫技解决。保留失败记录，才能让后来的人学习过程，而不是只复制结果。

## 36 最终项目定位

中国航天数字博物馆可以被定义为：**中国航天发展史交互式数字博物馆，同时也是一次完整记录 Human × ChatGPT × Codex 协作开发过程的实验项目。**

航天爱好者可以从五条主线和任务过程理解不同阶段的能力扩展；数字历史和数字博物馆开发者可以观察内容、展品、来源和展陈结构如何逐步分离；Three.js 学习者可以看到三维场景如何被限制在真正需要空间感的部分；AI Coding 和 Codex 用户则可以看到 Prompt、截图、QA、Git 和人工判断如何共同构成一个可持续迭代的工作流。

## 37 V5.0 不是结束

V5.0 首先是 PC 正式版。Mobile 和 Tablet 暂未正式支持，未来可能出现的 v5.0.1、V5.1、性能优化、更多开放授权资料或专题展项，都必须等待人工决定，不能被当前文档写成已经确定的路线图。

版本停止也是工程能力的一部分。继续增加内容并不一定提高展馆质量，继续调整视觉也不一定提高理解效率。V5.0 的正式冻结点，让项目可以被访问、复盘和验收，而不是一直等待一个不存在的“最终最终版”。

## 38 结语

AI 可以显著降低实现门槛，却不会自动替人完成判断。这个项目不是一次 Prompt 生成的，也不是某个模型单独完成的。它来自不断观察、发现问题、拒绝不满意结果、缩小范围、核对事实、运行 QA，再继续有限迭代的过程。

从一条时间轴到数字博物馆，最重要的变化不是页面拥有了多少模块，而是项目逐渐学会把内容、视觉、证据、用户体验和发布责任放在同一个系统里思考。Human 提供目的和判断，ChatGPT 提供分析和组织，Codex 把方案变成真实文件、页面和发布结果；三者之间持续往返，才让一个想法最终成为可以被别人打开的展馆。
